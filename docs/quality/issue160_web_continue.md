# #160 Web 继续本局：实现与收口边界

状态：开发验收中，不能据此关闭 #160 或发布。本文补充早期桌面切片，后者的 Web 不支持说明属于当时状态。

## 已实现的契约

- Web 使用单线程分帧回放；冻结的是独立历史值，不在帧间访问活跃 Run。恢复候选在接管前完成完整前缀、六条随机流、配置 manifest 和精确终点验证。
- v3 包以 little-endian binary64 标签保存浮点值。实际序列化文本重新解析、解码并独立回放通过后才能进入 Store；不降低未知版本、保留键、非有限数和深度限制。
- Store 在跨帧提交期间保持 busy；顺序仍为临时档验证、保留损坏原件、回滚日志、备档替换、主档替换、主备读回、退役日志。失败回滚保留原档；实际浏览器事务完成前不显示“已保存”。
- 检查点独立持久化于 IndexedDB `skill-lines-checkpoints-v1`，CAS 冲突或连接失效需重新加载。未知数据不自动清空。文件映射采用 canonical base64；同一读写事务内校验版本并写入，完成事件才确认。
- 采集独立使用 `skill-lines-telemetry-v1`，追加 JSONL 具有文件 CAS、总量限制及确认高水位。采集失败不阻止规则推进或检查点保存；检查点失败不抹去已确认采集。
- 恢复保持规则 run_id，创建新的采集 session/segment；只有验证实际持久前缀、事件 ID 和摘要后才声明已知父段，否则明确未知。不补造历史观察事件、结束时间或自然终局。
- 产品导出两步完成：先准备实际确认的数据库快照，再由用户点击下载 ZIP。文件原始字节、摘要、长度和不完整原因进入 manifest；失败仍允许导出已保存前缀。

## 本轮分帧优化

`9660636` 按记录分帧浮点传输和纯数据校验，拆开包构建与完整尺寸检查。实际 476 条 Web 合成前缀：保存最大帧间隔 261.5ms，恢复 177.5ms，源状态未变、恢复端点相等；保存总耗时 14.95s。不能只引用尖峰改善而隐去总耗时增长。

`c69daf0` 使用每 64 条或约 2ms 的工作片，逐条计算真实 JSON UTF-8 尺寸，避免一次整包 stringify 计数；保留所有纯值检查和上限。主、备读回及日志退役分帧，busy 持续到完成。单条复杂数据、JSON 解析及引擎调用仍不可抢占。

同一合成规则/种子最新实测：476 条记录保存 12.774s、最大帧间隔 244.3ms；恢复重建 9.0402s、最大帧间隔 163.8ms。最大载荷校验片保存 5.9ms/恢复 13.9ms，但 Store 最大片仍 241.5ms、包序列化 161.1ms。所有端点相等且源状态未变。该结果仍有明显尖峰和总时延，不能判定收口。

专项验证：此前五脚本 40/40、1094 断言；本轮 Store/Job/所有权三脚本 29/29、530 断言；浮点/分帧两脚本 14/14、780 断言，包括中文、转义、恰好 15MiB 与 +1 字节。独立静态复审通过，相关代码均不超过 500 行。失败的测试清单和旧测试假设记录保留，不算通过。
