# 技能连珠 · Git分支与发行策略

2026-10-20确定。适用于实际游戏仓库 `LiGameAcademy/GodotRogueMatcher`。课程工作区中的设计、教程和其他项目改动不混入游戏提交。

## 分支职责与命名

`master`保持默认保护分支，承载验收后的稳定版本。每个里程碑拥有一个开发主分支；功能、重构、调试和修复按issue拆成可审阅切片。

| 分支 | 示例 | 创建起点 | PR目标 |
| --- | --- | --- | --- |
| 稳定主干 | `master` | 已验收版本持续演进 | 接收发行分支或稳定版紧急修复 |
| 里程碑开发主分支 | `develop/0.0.3` | 启动里程碑时的最新稳定`master` | 验收候选从此创建发行分支 |
| 功能、重构、核查 | `feature/132-compatibility-baseline` | 对应`develop/<版本>` | 原开发分支 |
| 调试与缺陷修复 | `fix/137-status-localization` | 缺陷所在的开发、发行或稳定分支 | 原起点分支 |
| 发行候选 | `release/0.0.3` | 对应开发分支的明确候选提交 | 验收通过后合入`master` |

使用小写英文、数字、斜杠及连字符，不含空格。功能与修复分支格式为`feature/<issue号>-<简短用途>`、`fix/<issue号>-<简短用途>`；同一issue分多片时使用不同用途后缀。数字指issue号，不是PR号；PR创建后再获得自己的编号。不另设`debug/`或长期`refactor/`分支，重构归`feature/`，缺陷定位及实验修复归`fix/`。

发行默认格式为`release/<版本>`，当前单一Web发布使用`release/0.0.3`，平台配置保存在导出预设与构建记录中。发行分支用于冻结候选范围，使验收与后续开发可以并行；不要求每个平台一条分支。平台确有独立修改、验收或发布时间差异时，才使用`release/<版本>-<平台>`。`release/0.0.3-wechat`仅是命名示例，不代表授权增加微信平台；避免使用缺少版本的`release/wechat`，不提前建立空分支。

## 开发与PR

1. 从目标开发分支同步后的明确提交创建issue分支，记录起点；不从旧`master`、未合并试作或其他功能分支盲开。
2. 完成当前切片、必要验证与中文提交后，向对应开发分支提交关联PR。完整解决issue才使用`Fixes #编号`，部分交付使用`Refs #编号`。
3. PR提供范围、规则依据、验证结果与未测限制。复杂规则或交互变更留作者review及编辑器试玩，不自动合并。
4. PR分支有冲突时，将最新目标分支合入并复验受影响内容；已共享分支默认不rebase、不强推。个人未共享提交可在推送前整理。
5. 功能默认独立起片；确需堆叠依赖时写明父PR及临时base，父PR合并后调整到开发分支再验收，不能误带未授权内容。

`master`通过PR更新，保留保护规则及所要求的检查，不直接推送、不强推、不删除。开发主分支保持可追溯，默认也通过PR集成。分支合并采用merge commit保留切片历史，不以squash/rebase重写已共享历史。保护设置的实际状态应在仓库设置核验，本文不声称已启用或修改任何GitHub设置。

## 发行与修复回流

1. 里程碑功能范围具备候选条件后，从`develop/<版本>`创建`release/<版本>`，确需独立平台发行才带平台后缀；记录候选SHA、引擎、配置与构建身份。发行分支冻结范围，只接收发行所需修复、版本信息、构建及验收证据。
2. 发行候选有缺陷，从该发行分支创建`fix/<issue号>-<用途>`，PR回发行分支。修复合并后，将发行分支通过PR回流对应开发分支，避免只修发行候选；同一修复默认不重复cherry-pick。
3. 按该里程碑门槛完成技术验证、作者review及目标平台验收后，将发行分支PR合入`master`。未通过不得因预算或日期触顶降低门槛。
4. 合入后核对`master`与验收候选的文件树及构建身份。正式tag指向最终验收的`master`提交；仅合并元数据变化且文件树相同时可以复用已验证构建，记录候选/合并/tag/包哈希对应关系；内容变化则按影响复验。
5. 创建tag、上传GitHub/itch等发行物仍需实际发布授权，合入`master`不自动等于公开发行成功。已发布tag和包不覆盖；需要修正时使用新的补丁版本。
6. 发行后，将`master`通过PR回流仍在维护的相关开发分支，随后下一里程碑从最新稳定`master`建立新的`develop/<版本>`。不从已偏离的历史开发分支延续新里程碑。

稳定版紧急缺陷从最新`master`创建`fix/<issue号>-<用途>`，必要验证和作者review后PR回`master`，再回流受影响的开发/发行分支。若下一版功能已在开发，不将整条开发分支带入稳定版修复；重新发行按补丁版本及相同平台验收流程执行。

## 同步与清理

- 开工前核对`status`、当前分支、远端和worktree占用；`fetch --prune`同步引用，更新本地主分支使用`--ff-only`。已有修改先保留，不用reset/clean掩盖差异。
- 功能/修复分支仅在PR已合并、提交已被目标包含、无开放PR和其他用途、未被worktree占用后删除远端及本地分支。默认本地使用`git branch -d`，不为清理强删未合并成果。
- 发行分支在发行及必要回流完成、有稳定tag和证据后删除；里程碑开发分支在该版结束、必要回流完成且不再维护后删除。历史由tag、PR和提交保留，不长期积累无用途分支。
- 未合并试作、备份、其他worktree占用及来源不明分支先保留并说明原因；不能仅凭名称或时间判定无用。清理其他remote需单独核对其用途，不默认将GitHub清理扩展到Gitee。
- 不删除或改写`master`、发行tag、作者未提交修改。工作区外层的设计修改保持独立，不因游戏子仓库干净而丢弃。
